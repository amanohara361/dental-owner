# 運用メモ（定時実行の仕組みと既知の制約）

最終更新: 2026-08-09

## 定時実行の構成

**重要**: 各トラックは「毎回まっさらなセッションを立てる」方式では**動かない**。
リポジトリと認証情報を持った**常設の実行セッション**を1つ用意し、
Routine（スケジュール実行）はそこへ指示を送る構成にしている
（Routine の `persistent_session_id` に実行セッションを指定）。

| トラック | 実行 (JST) | cron (UTC) | 手順書 |
| --- | --- | --- | --- |
| 法令・手続き・人事 | 月 17:00 | `0 8 * * 1` | `prompts/regulatory.md` |
| 財務 | 火 08:00 | `0 23 * * 1` | `prompts/weekly-finance.md` |
| 立地 | 木 13:00 | `0 4 * * 4` | `prompts/weekly-location.md` |

実行セッション: 「歯科開業アドバイザー 実行セッション **v3**」
（`source_url` にこのリポジトリと作業ブランチを指定して作成したもの）。
**このセッションを消すと3本とも動かなくなる。**

**ネットワーク設定はセッション開始時にしか読み込まれない。**
環境の許可ドメインを変えたら、実行セッションを立て直して
Routine 3本を新セッションへ張り替える必要がある。
初代（8/7 作成）と v2 は、2026-08-09 のネットワーク設定変更を取り込むために
作り直したもので、いずれもアーカイブ済み。

## 既知の制約1: 新規セッションにはリポジトリも認証情報も渡らない

**2026-08-07 に判明。初回の試走が失敗した原因。**

Routine が新しいセッションを立てる方式（`create_new_session_on_fire`）では、
起動したセッションの作業ディレクトリにリポジトリが存在しない
（`no git repository found in /home/user`）。手順書もチェックリストも読めない。

さらに、プロンプト内で `git clone` させる回避策も**この経路では機能しない**。
リポジトリの認証情報が渡らないため。

### 検証結果（2026-08-07）

| 起動経路 | リポジトリ | push | 結果 |
| --- | --- | --- | --- |
| 新規セッション（指定なし） | 無し | — | 失敗 |
| 新規セッション（プロンプト内で clone） | — | — | 失敗 |
| `create_session` に `source_url` 指定 | 有り | 可 | 成功 |
| `create_session` から自力 clone（親セッション有り） | 有り | 可 | 成功 |
| **Routine → 常設セッション（スケジュール発火）** | 有り | 可 | **成功。この構成を採用** |

### 落とし穴: 手動実行は挙動が違う

`fire_trigger` による**手動実行は `persistent_session_id` を無視し、
新しいセッションを起こす**。そのため手動実行は失敗し、
スケジュール発火は成功する、という食い違いが起きる。

**手動実行の失敗をもって「壊れている」と判断しないこと。**
検証したい場合は、数分先を指定した1回限りの Routine（`run_once_at`）を作る。
これは本物のスケジュール経路を通る。

## 既知の制約2: `WebFetch` は大部分が開通。ただし全ドメインではない

**2026-08-09 に環境のネットワーク設定が変更され、再実測した。**
2026-08-07 時点の「実質すべての外部サイトがブロック」という記述は、
現在の実態と異なるため破棄した。

### 実測結果（2026-08-09）

| ドメイン | 結果 |
| --- | --- |
| `www.mhlw.go.jp`（厚生労働省） | 取得成功 |
| `www.jfc.go.jp`（日本政策金融公庫） | 取得成功 |
| `www.e-stat.go.jp`（政府統計の総合窓口） | 取得成功 |
| `elaws.e-gov.go.jp`（e-Gov 法令検索） | 301 で `laws.e-gov.go.jp` へ転送。転送先で取得成功 |
| `www.stat.go.jp`（総務省統計局） | 取得成功 |
| `www.city.saitama.lg.jp`（さいたま市） | 取得成功 |
| `www.city.kita.tokyo.jp`（東京都北区） | **`EGRESS_BLOCKED`**（`*.tokyo.jp` 追加前。後述のとおり解消） |

つまり **2026-08-07 に「ブロック」と記録したドメインの多くは、現在は通る**。
一方で **許可は全ドメインには及んでおらず、個別に落ちるものがある**。
未確認のドメインが通るかどうかは、実行時に試すまでわからない。

### 再実測（2026-08-09、許可ドメインに `*.tokyo.jp` を追加した後）

立地トラックの次回対象（東京23区北部）のドメインを実測した。
**北区の `EGRESS_BLOCKED` は解消**している。

| URL | 結果 |
| --- | --- |
| `https://www.city.kita.tokyo.jp/` | 301 で `https://www.city.kita.lg.jp/` へ転送。**転送先を指定し直して取得成功**。`EGRESS_BLOCKED` は出ない |
| `https://www.city.itabashi.tokyo.jp/`（板橋区） | 取得成功 |
| `https://www.city.adachi.tokyo.jp/`（足立区） | 取得成功 |
| `https://www.city.arakawa.tokyo.jp/`（荒川区） | **HTTP 503 Service Unavailable**。`/index.html` でも再現。`EGRESS_BLOCKED` ではなく、リクエスト自体は到達している |
| `https://www.city.toshima.lg.jp/`（豊島区） | 取得成功 |
| `https://www.metro.tokyo.lg.jp/`（東京都） | 取得成功 |

**北区は現ドメイン `www.city.kita.lg.jp` へ移行済み**。
`*.tokyo.jp` の追加で旧ドメインへの到達自体は通るようになったが、
転送先は `.lg.jp` なので、**最初から `https://www.city.kita.lg.jp/` を叩くのが速い**。

荒川区の 503 は egress の遮断とは切り分けられている。ただし
**原因（サイト側の一時障害か、ボット避けの応答か）は未確認**。
立地トラック実行時に再度試し、なお 503 なら二次情報として扱う。

`elaws.e-gov.go.jp` は現在 `laws.e-gov.go.jp` へのリダイレクトになっている。
`WebFetch` はホストをまたぐリダイレクトを自動で追わないため、
**転送先 URL を指定して呼び直す**必要がある。

Web検索（`WebSearch`）は従来どおり通る。

### 実行時にまず確認すること

調査対象のドメインに `WebFetch` を試す。`EGRESS_BLOCKED` が返った場合は、
そのドメインについてのみ**二次情報として扱う**。全滅を前提にしない。

### 対処

- 一次情報を直接確認できなかった項目は、レポートに**「未確認・二次情報」と明記**する。
  数字を確定情報として書かない
- 融資条件・施設基準・届出要件など、外すと損害が出る項目は
  「窓口で要確認」を必ず添える
- 個別にブロックされるドメインが残っているため、必要なドメインが落ちた場合は
  claude.ai の環境設定で許可ドメインを追加する。
  **`*.tokyo.jp` は 2026-08-09 に追加済み**（北区の `EGRESS_BLOCKED` はこれで解消）
- `EGRESS_BLOCKED` と HTTP エラー（503 など）を混同しない。
  **前者は環境の許可ドメイン設定の問題、後者はサイト側の応答**で、打つ手が違う

## トラブル時の切り分け手順

レポートが出ていないときは、次の順で確認する。

1. リモートブランチに新しいコミットがあるか
   （`git ls-remote origin refs/heads/claude/dental-startup-advisor-ctrpar`）
2. **実行セッションが生きているか。** これが消えていると3本とも動かない
3. Routine が有効か、`persistent_session_id` が実行セッションを指しているか、
   `next_run_at` が想定どおりか
4. 切り分けには、調査をさせず git 操作だけを実行させる**最小プローブ**を、
   `run_once_at` で数分先に仕掛けるのが速い（手動実行では経路が違うので不可）
